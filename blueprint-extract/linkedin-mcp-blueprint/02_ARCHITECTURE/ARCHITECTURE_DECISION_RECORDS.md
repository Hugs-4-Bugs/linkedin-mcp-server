# Architecture Decision Records

## ADR-001: TypeScript MCP core
Status: proposed/approved by blueprint owner. Reason: first-party MCP SDK maturity and integration velocity. Java remains viable but not selected.

## ADR-002: Modular monolith
Start with clear module boundaries; avoid premature microservices.

## ADR-003: Official LinkedIn API only
Do not use scraping, cookie auth, private endpoints, or bypasses.

## ADR-004: Monetization-ready interfaces, not monetization MVP
Build identity, tenant, quota and entitlement seams. Implement payments only after validation and owner approval.

## ADR-005: MCP TypeScript SDK v2 line (owner-approved 2026-11-26, decision D-A2)
Pin `@modelcontextprotocol/server` **2.4.0** (Apache-2.0, Node ≥20, implements 2026-07-28 MCP spec). Verified 2026-11-26 via npm registry. v1 (`@modelcontextprotocol/sdk` 1.32.2, 2025-11-25 spec) is the documented fallback if a verified Claude/ChatGPT/OAuth/Streamable-HTTP/stdio blocker appears; any switch requires evidence documented in a new ADR. Version bumps require ADR update — never silent.

## ADR-006: One codebase, two transports (owner-aligned, Phase 0 D-003)
stdio adapter (`serveStdio` from `@modelcontextprotocol/server/stdio`) for local dev; Streamable HTTP for staging/remote. No feature logic in transport layers.

## ADR-007: PostgreSQL for hosted persistence (staging/production)
Managed Postgres for staging+prod (tokens, tenants, usage, audit). Local dev runs ephemeral in-memory stores; no LinkedIn network calls in unit/protocol tests. Selected over SQLite-at-rest for relational tenant isolation and audit integrity.

## ADR-008: Envelope-encrypted token vault
LinkedIn access tokens (60-day bearer tokens) encrypted at rest: per-row DEK, KMS/secret-manager KEK. No plaintext tokens in DB, logs, or tool output. Enforced from Milestone 2 onward.

## ADR-009: LinkedIn adapter pins API versions
Adapters pin and track LinkedIn API versions (202611 current; 202601 sunsets 2027-01-15); version changes are reviewed changes with tests.

## ADR-010: Retention-by-class storage
Every persisted LinkedIn-derived field carries a retention class per Marketing API storage requirements (other-member profile 24h; member social 48h; org social 6w/6m; org profile 8w; aggregates 1y) with a TTL sweeper enforcing expiry. Implemented with storage layer (M2+).

## ADR-011: Graphify advisory-only, code-only local mode (owner-approved D-A9)
Use `Graphify-Labs/graphify` (PyPI `graphifyy`, Python 3.11.5–3.14; local tree-sitter parsing) in `--code-only` mode with no LLM backend (`GRAPHIFY_BACKEND=none`); nothing leaves the machine; `graphify-out/` is gitignored. Output is advisory navigation context; it never replaces tests, code review or architectural verification. Install deferred until a codebase exists.

## ADR-012: MVP tool surface = self-serve scopes only (owner-approved D-A1)
`openid profile email w_member_social`. Org/analytics/search/messaging/invitations are BLOCKED until independently verified and owner-approved. Deployment: local + staging only; no public production (owner D-A3); private-pilot posture (D-A6).

## ADR-013: Granted-scope truth model — token-response claim, never requested-as-granted (M3)
LinkedIn self-serve OAuth v2 exposes NO scope-introspection/tokeninfo endpoint (verified in Phase 0 research); the only granted-scope signal is the `scope` string returned by the token-exchange response, captured at connect time (M2 vault). M3 therefore represents scopes as a truth model: `requestedScopes` (fixed set asked at authorize), `tokenScopeClaim` (what the exchange response said), `verification: 'token-response' | 'unverified'` (unverified = no claim captured), `missingFromClaim`, `connectionState` (connected/expired/disconnected). The `linkedin_list_granted_scopes` tool reports this model and states the introspection limitation explicitly in its output note. We never equate requested with granted, and we never claim live verification we cannot perform.

## ADR-014: Profile capability = OIDC userinfo with strict response validation (M3)
`linkedin_get_my_profile` calls `https://api.linkedin.com/v2/userinfo` (OIDC) with the tenant's sealed access token — identity comes from the token, never from arguments (the tool schema is `{}` strict, so member substitution is impossible by construction). Responses are validated against a permitted-field allowlist (`sub`, `name`, `given_name`, `family_name`, `email`, `email_verified`, `locale`, `picture`); unexpected fields are REJECTED, not dropped. Provider errors map to safe structured tool errors (`provider-timeout`/`provider-http-status`/`provider-invalid-response`/`provider-network`); response bodies never enter logs or errors. The real provider enforces a 10 s AbortController timeout; 401/403 are surfaced as reconnect guidance. The mock provider serves deterministic fixtures that must themselves pass validation (self-checking mock).

## ADR-015: Publishing limits are application safety limits, NOT claimed LinkedIn quotas (M4)
Phase 2 verification (2026-11-27, Microsoft Learn "API Rate Limiting" page): LinkedIn documents that all API requests are rate limited per day, but **publishes no numeric per-member or per-app quota** — actual limits are surfaced per-app in the Developer Portal Analytics tab, and 429 signals throttling. The "150 posts/member/day" figure carried in earlier notes is community folklore with no official source and is RETRACTED as a claimed quota. M4 therefore separates three limit layers: (1) official platform limits — represented as "not published; enforced by LinkedIn via 429" with no invented numbers; (2) application safety limits — configurable `PUBLISH_DAILY_LIMIT` (default 12, hard ceiling 100) and `PUBLISH_DUPLICATE_WINDOW_MINUTES` (default 10) enforced via per-tenant token buckets and the operation ledger; (3) tenant quotas — same per-tenant budget mechanism. Configuration can only tighten or bounded-widen safety limits; there is NO configuration path that bypasses authorization, scopes, or the confirmation gate (code-enforced, not env-enforced). The prior M2/M3 note claiming 150/day documentation is corrected in `provider.ts`.

## ADR-016: Publication duplicate/write safety — local operation ledger, honestly bounded (M4)
LinkedIn's Posts API provides NO idempotency mechanism (no idempotency-key header; the only duplicate-related server behavior is a 422 exact-duplicate response, which is not a contract to rely on). M4 implements a LOCAL operation ledger (`PostOperationStore`, in-memory like the rest of the M2/M3 state): content-hash (SHA-256) + tenant keyed records with (a) an in-flight lock — an identical publish already running is refused; (b) a completed-attempt window — identical content within `duplicateWindowMs` is refused (`duplicate-recent-identical`); (c) ambiguous-outcome marking — timeout/network/5xx after send records the hash as suspect and refuses identical resubmission with guidance to verify out-of-band. Provider writes are NEVER auto-retried (an uncertain write retried is exactly how duplicate posts get created); failure (definite 4xx) is user-retryable. Stated limitations: this is NOT exactly-once publishing — a timeout after LinkedIn accepted the post, a process restart, or a second process instance can each still produce a duplicate; persistence arrives with the M5 Postgres ledger.

## ADR-017: Publishing capability = Posts API text-only member posts (M4)
`linkedin_publish_post` calls `POST https://api.linkedin.com/rest/posts` (Posts API — the current API that replaces ugcPosts) with the documented text-post schema: `author: urn:li:person:{sub}` (member OIDC sub from the sealed token; callers cannot supply an author), `commentary`, `visibility: PUBLIC`, `distribution: {feedDistribution: MAIN_FEED, targetEntities: [], thirdPartyDistributionChannels: []}`, `lifecycleState: PUBLISHED`, `isReshareDisabledByAuthor: false`; headers `X-Restli-Protocol-Version: 2.0.0` + `Linkedin-Version: 202611` (ADR-009 version pinning); success is 201 with the post URN in the `x-restli-id` header (empty body — a body claiming success is never trusted). Commentary is capped at 3000 characters (documented UGC/Posts text limit) and blank/control-char content is rejected locally. Provider errors classify as: 4xx = definite refusal; timeout/network/5xx = ambiguous (outcome unknown — surfaced, never retried automatically). Media, mentions, targeting, reshares, dark posts and organization-authored posts are OUT OF SCOPE for M4 (the official docs require media asset uploads / org scopes we do not hold). The member sub → `urn:li:person:{sub}` author mapping is community-verified (n8n thread: userinfo sub is the URN id), not stated in official docs — flagged in HANDOFF_M4 as a to-verify-on-live item.

## ADR-018: Persistent storage via a SQL executor seam (M5)
PostgreSQL (ADR-007 reaffirmed for staging/production) reached implementation: a narrow `SqlExecutor` interface (`src/storage/sqlExecutor.ts`) with two implementations — `PostgresExecutor` (pinned `pg@8.16.0`, the blueprint's intended client; the only dependency added in M5, justified by the milestone's persistence requirement) and `SqliteExecutor` (Node built-in `node:sqlite`, zero dependencies) for local dev + deterministic integration tests. One migration list (`src/storage/migrations.ts`, dialect variants per step) runs idempotently at startup. All stores keep their M2–M4 contracts behind SQL implementations (`SqlTokenVault` — SAME AES-256-GCM envelope, DB stores ciphertext only; `SqlOAuthStateStore` — atomic single-use consume; `SqlPostOperationStore`/`SqlPublishBudget` — transactional). Placeholder discipline: numbered (`?N`/`$N`) parameters only; no value interpolation; timestamps passed as parameters (dialect-neutral). When `DATABASE_URL` is unset, `buildPersistentRuntime` is byte-identical in behavior to the M4 in-memory runtime — the 166 M1–M4 regression tests prove it. Known limits: SQLite executor is single-process by design; the Postgres transaction executor serializes per checkout (concurrent `with()` calls take separate pool clients, each internally consistent; cross-transaction isolation relies on row-level semantics).

## ADR-019: Remote authentication = credentials only, never caller-supplied tenants (M5)
The remote HTTP surface authenticates per request from a REAL credential: a session cookie (HttpOnly, SameSite=Lax, Secure outside local; opaque 256-bit token stored as SHA-256 digest — a DB leak yields no usable sessions) or a bearer API token (same digest scheme, `lkm_`-prefixed). Passwords: scrypt N=16384 with per-user salt, constant-time verify, uniform failure messages (no user enumeration). CSRF: per-session token, double-submit + digest comparison on state-changing routes. The authenticated tenant is carried to the tool layer by AsyncLocalStorage (`src/identity/requestTenant.ts`) — a caller-supplied tenant header is never read anywhere. Two real bugs were found and fixed by the E2E suite: (1) the MCP SDK's lazy server factory resolved tool contexts outside the request's ALS scope — tool contexts are now built per tool call; (2) the OAuth routes constructed a hand-rolled tenant whose `userId` diverged from `LOCAL_DEV_TENANT`, splitting the vault key space — routes now reuse the canonical tenant objects. Production startup rejects mock auth (and mock OAuth, and missing persistence/vault key) — fail-fast, not silent fallback. stdio remains credential-free on the local tenant (unchanged).

## ADR-020: Operator console = one self-contained page speaking MCP itself (M5)
`/admin` serves a single HTML page with no build step and a strict CSP (`default-src 'none'; script-src 'self'` — everything inline in the served document, zero external assets). It is a REAL client: it runs `initialize` → `tools/list` → `tools/call` against `/mcp` with the session cookie, and drives `/auth/*` + the OAuth routes. Every state shown derives from actual responses; nothing is mocked. Publishing goes through the SAME `confirm:true` schema gate as any MCP client — the UI arms an explicit checkbox + browser confirm before sending it, and cannot bypass backend authorization because no client-side path can. Design: restrained radii (2–4px), strong typographic hierarchy, subtle 1px borders, dense tables, purposeful motion only (fade on view switch; `prefers-reduced-motion` respected) — explicitly avoiding the generic-AI-template look (no glassmorphism, gradient blobs, icon-per-card, oversized rounding). Where a UI is NOT appropriate: API-token issuance (secret material shown once at creation — CLI/ops workflow), and raw MCP stdio usage (protocol client territory) — documented rather than half-built.

## ADR-021: Real-PostgreSQL integration testing via embedded-postgres (M6)
The M5 PostgresExecutor was verified only through SQLite-equivalence (no PG server in that sandbox) — a flagged residual risk. M6 closes it: `embedded-postgres@19.0.0-beta.20` (devDependency only; runtime deps unchanged) runs a REAL PostgreSQL 19 server in CI/local (initdb + server + wire protocol; compose pins postgres:17 — same dialect surface: DDL, `INSERT … ON CONFLICT`, TIMESTAMPTZ, numbered `$n` placeholders, transactions). The suite (`tests/integration/pg-integration.test.ts`, 15 tests) found and fixed a REAL bug: concurrent `SqlPublishBudget.take()` calls on separate pooled clients raced read-modify-write and exceeded capacity (lost update) — fixed with `SELECT … FOR UPDATE` row locking on the Postgres path (SQLite serializes writers natively). Also verified: migration idempotency on real PG, transaction ROLLBACK, digest-at-rest sessions, restart survival on a persistent cluster. The staging story gains `src/scripts/preflight.ts` (env/secret/DB/migration preflight; PG-verified) and `deploy/staging-smoke.sh` (10-check live-host smoke; validated 10/10 against a live local deployment rehearsal). A live 17.x host bring-up remains the owner's staging action.

## ADR-022: Retention enforcement as a first-class runtime subsystem (M7)
ADR-010/D-006 specified per-class retention with a TTL sweeper but M5 shipped only the schemas; issue #16 closed the gap. `RetentionSweeper` (src/storage/retention.ts) enforces per-data-class TTLs via DELETE (sessions past expiry; revoked API tokens past a 24h grace; expired oauth_states; ended publish_operations past the duplicate window; audit_log past AUDIT_RETENTION_DAYS, default 90d; orphaned publish_budgets past one window) with dialect-portable ISO-parameter comparisons — the same pattern the OAuth state store uses. `PeriodicSweeper` runs a boot sweep plus an unref'd interval (RETENTION_SWEEP_INTERVAL_SECONDS, default 1h, 0 = boot-only) and is stopped at graceful shutdown. Account removal (`UserAuthStore.deleteUser`) deletes the user and every tenant-keyed row in ONE transaction (sessions via FK cascade; vault/api_tokens/ledger/budgets/audit explicit). Tool-call audit coverage closes the toolPolicy.audit wiring gap: every registered tool dispatches through `auditedRun`, which records tool name + outcome (identifiers only, never payloads); audit failures are log-only and can never mask a tool result. Verified by tests/security/retention.test.ts (9 tests) and two real-PostgreSQL tests in pg-integration.test.ts; THREAT_MODEL.md/DATA_PRIVACY.md now carry the verified evidence (issue #12).
