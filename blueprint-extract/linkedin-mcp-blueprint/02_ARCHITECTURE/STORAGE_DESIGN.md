# Storage Design

Use PostgreSQL if hosted multi-user persistence is required. Tables/entities initially: users, tenants (or workspace), tenant memberships if multi-user, linked accounts, OAuth credential references/encrypted token material, scopes/permissions, usage records, subscription/entitlement records (future), audit events, consent records and operational metadata.

Minimize stored LinkedIn content; prefer transient processing. Define retention and deletion. Token material must be encrypted with managed key strategy, not plain database text. Use migrations, constraints, tenant-scoped queries and backup/restore tests.

## M5 implementation state (2026-11-27)

Persistent storage is implemented per ADR-018: `SqlExecutor` seam (`src/storage/`) with Postgres (`pg@8.16.0`, staging/production) and SQLite (`node:sqlite`, local/dev/tests) backends; one idempotent migration list (`migrations.ts`, dialect variants). Tables: `users`, `sessions`, `linkedin_tokens` (AES-256-GCM ciphertext only — same envelope as ADR-008; tenant_id is the primary key so cross-tenant reads are structurally impossible), `oauth_states` (single-use via atomic conditional UPDATE), `publish_operations` (content-hash ledger; PK = tenant+hash), `publish_budgets` (transactional read-modify-write), `api_tokens`, `audit_log`, `schema_migrations`. Every tenant-owned query filters by tenant_id. Transactions: explicit `with()` (BEGIN/COMMIT/ROLLBACK; SQLite serialized per connection, Postgres per pool checkout — see ADR-018 concurrency notes). Deletion: disconnect removes the token row (tombstone-free by design); sessions revoke (soft) so audit history stays; no other LinkedIn-derived data is persisted (scope rows store scopes strings only). Unset `DATABASE_URL` = the in-memory M2–M4 runtime (dev/stdio unchanged).
